# DECISIONS

- Stack S over Vercel+Firebase for few-users simplicity: Cloudflare Workers (100k req/day free, commercial OK) + Upstash Redis Free (500k cmds/mo, TTL-native) + D1 (receipts durability). Memory cache remains as fallback interface.
- SPA (Vite) + Hono worker in one Worker project instead of Next.js App Router (avoids next-on-pages CPU/RAM friction, keeps lib/ pure TS portable).
- Banned-words vs NO_MATCH wording conflict (§0.6 vs §4.7 "does not mean it's fake"): honest meaning preserved as "That does not mean it is not real." so the guardrail test passes. Guardrail uses whole-word match (avoids false positives like "replies" containing "lie"); banned list lives only in the test file, never in copy.ts.
- CDX discovery: SPEC ID-prefix-bucket search now SHIPPED (worker/wayback/cdx.ts drives lib/wayback/buckets + buildCdxUrl/parse/dedupe/filter — no duplicate parsers). Capture-time `from=` lower bound ONLY (never `to=` — a capture can postdate the post by years). x.com buckets first, twitter.com as fall-through when x.com yields nothing (same tweet IDs, halves typical volume); bucket fetches capped at concurrency 3 against the archive's ~60 req/min ceiling. Exact Snowflake ID-time filter client-side.
- Pre-2010 (non-Snowflake) IDs: kept in candidate set (idTimeMs 0 = unknown) rather than dropped, since their Snowflake decode is meaningless.
- Screenshot date window: SPEC ±50h ([date 00:00 − 14h, 23:59 + 12h] UTC) in src/lib/check-client.ts windowFromParsed.
- vite 5.4.x (not 6): vitest 2.1.8 bundles vite 5 types; vite 6 breaks vitest.config.ts typecheck. Revisit on vitest 3.
- Strong-OCR track (PaddleOCR PP-OCRv5 mobile EN, on-device, $0): models vendored under public/paddle/ from HuggingFace `OllmOne/PP-OCRv5` (Apache-2.0, paddle2onnx mirror of official PaddleOCR; no official Paddle .onnx release exists) — det `pp-ocrv5_mobile_det.onnx` (4,826,518 B), rec `en_pp-ocrv5_mobile_rec.onnx` (7,876,014 B), dict `ppocrv5_en_dict.txt` (1,416 B, 436 chars incl `-`/`@`, no space line) — total ~12.4MB, each file < 25MiB single-file limit. Fallback considered but not vendored: `SWHL/RapidOCR` PP-OCRv4 det (4,745,517 B) + PP-OCRv3 EN rec (8,967,018 B). onnxruntime-web pinned to 1.19.0 (MIT): its default bundle references the classic ~10.5MB threaded-SIMD wasm run single-threaded (numThreads 1, no COOP/COEP); ORT ≥1.22 defaults to a ~28MB JSEP build (breaks the 25MiB deploy limit) whose extern-wasm variant cannot load its `.mjs` glue under the vite dev server (measured). vite needs `optimizeDeps.exclude: ['onnxruntime-web']` in dev, else esbuild pre-bundling serves HTML for the `.wasm` URL ("expected magic word" at instantiate). First-load JS stays ~101-103kB gz (< 150kB budget); paddle-engine (~3.5kB gz) + ort (~108kB gz) + ort wasm (10.5MB) are lazy on-demand chunks. Rec head emits 438 classes = 436 dict + SPACE + CTC blank (training `use_space_char: true` appends space; verified against official `en_PP-OCRv5_mobile_rec` inference.yml: image_shape [3,48,320], CTCLabelDecode). Width axis is dynamic so rec runs uncapped (upstream 320 cap is for batching; squeezing full-width lines to 320 crushes glyphs and blanks the decode — measured). Some paddle2onnx exports already end in Softmax: per-row sum ~= 1 detection skips the second softmax (else confidences collapse to ~1). Per-box Otsu-anchored soft contrast expansion ([0..64]/[192..255]) fixes dim-gray UI text misreads ('t'->'l', ':'->'1') without the 'O'->'Q' notching hard binarization caused (all measured A/B on the dark replica). Hyphen honesty: the replica wraps at "Jae-|myung", so detection yields two boxes and parse joins with a space — literal "Jae-myung" is unreachable on this replica for either engine (Tesseract corrupts to "Jaemyung"; Paddle preserves "Jae myung" uncorrupted). A/B numbers in the strong-OCR track report.
